OpenWebUI for Administrators: Multi-User Access, Permissions, and Conversation Controls

Basho Parks

Updated October 28, 2026: I wrote this against the April 2026 release. OpenWebUI sits at v0.12.4 as of October 25, 2026, and v0.12.0 (October 10, 2026) added realtime voice calls; admin screens move between releases, so the menu paths below are a map, not a script. Pin the version you deploy, update on a schedule you set rather than on release day, and re-check admin roles and retention settings after every upgrade.

An on-premise AI system without an admin plan is a compliance problem wearing a nice interface.

OpenWebUI's the standard open-source interface for local language models; it handles user permissions, conversation history, and usage logging without shipping a byte to a cloud platform. This is the walkthrough I run with an admin on site, in the order I run it; it assumes the hardware's standing, not where it came from.

Initial Setup and Admin Login

OpenWebUI runs in Docker on your local network, reachable at http://ai.yourfirm.local:8080. The first user created becomes the admin, so get there before somebody's nephew does.

The admin password controls everything, so make it 20-plus characters and keep it in whatever vault your firm already runs. Then, before anything else: disable public registration, require authentication for all access, and set the retention window covered below. I don't leave a site until those three are done; they're the ones that cost people later.

User Accounts and Roles

OpenWebUI's roles are Admin and User. Admins change settings, Users reach models and can't touch configuration.

Admin Settings, then User Management, then Add User: username, password, role. A law firm thinks in Attorney, Paralegal, and Staff, and OpenWebUI doesn't map those onto models natively, so create the accounts first and restrict the models second. Restrict first and the new hire sees nothing.

Model Access by Role

This is the step I won't prescribe from a blog post. Which models sit on your box depends on what Discovery turned up, and who reaches which one on what those people do all day; I don't know that yet and neither does a checklist. In a law firm that's usually attorneys and senior paralegals on every model, junior paralegals on everything but the model handling live matters, and administrative staff on one summarization model.

Under Models in Admin Settings, each model carries an access list naming who can reach it. Keep a spreadsheet of who should reach what and reconcile it against the panel monthly; it's cruder than enterprise IAM, auditable, and free.

Conversation History and Retention

Every conversation lives in a SQLite database on the server, for example /root/ollama/web/conversations.db; the exact path depends on your deployment. That's the compliance advantage in one sentence, and the responsibility too: retention, backup, and access are yours now.

The Conversations tab shows every conversation across every user, searchable and exportable as JSON with timestamps, model, user, and full text: when a discovery request lands, that's your record.

Set the retention window under Admin Settings, then System, then Conversation Retention: 365 days for law firms holding litigation-hold capability, 180 for medical practices, 90 for IT support. Where conversations carry protected health information, all of that has to satisfy HIPAA: encrypt the database at rest and be able to name every person who reaches the admin panel.

Usage Monitoring

Analytics, once you've enabled it, logs which user ran which model and when, plus the odd spike, like somebody running hundreds of queries a day, usually a script and not a motivated paralegal. That's enough to track adoption and catch anomalies; it isn't a SIEM and I won't pretend otherwise.

Network: Static IP, Hostname, VPN

Give the server a static IP so it doesn't pull a new address on reboot and a hostname like ai.yourfirm.local in your internal DNS or hosts file; nobody's memorizing an address.

The server doesn't go on the internet, not even for the consultant who asked nicely; remote staff come in over a VPN. Tailscale's the easiest path, an encrypted mesh limited to devices in your account; WireGuard does the same self-hosted with more configuration and no cloud intermediary. I'd put "no direct internet exposure" in writing before the machine's powered on.

Backups

A daily cron job backs the database up to a local NAS or external drive:

sqlite3 /root/ollama/web/conversations.db ".backup /mnt/nas/backup/conversations-$(date +\%Y\%m\%d).db"

Keep 30 days of dailies on encrypted local storage, and don't sync them to S3, Google Drive, or Dropbox. You've got hardware in the building to keep this data off cloud platforms; syncing the backups hands it all back.

Getting Started

The checklist, in order: admin password, registration off, users with roles, models restricted by user, retention set, static IP and hostname, VPN, backups.

That's the easy half. What a checklist can't hand you is which of your people needs which model. I learn that by shadowing the people who run the workflow; the access map follows from what they do, and configuring it together on site is where a deployment takes or doesn't. For HIPAA, FERPA, or SOC 2 obligations, reach us and we'll walk your audit and retention requirements directly.

Summary: OpenWebUI brings user management, per-model access, retention control, and usage logging to a local deployment without touching a cloud platform. Disable public registration, restrict models per user, set retention, keep the server behind a VPN, and back the database up nightly to local storage.
